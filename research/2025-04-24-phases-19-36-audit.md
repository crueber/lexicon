## Research Question

For each implementation phase 19 through 36 in `plans/2026-03-23-lexicon-implementation-plan.md` Section 27, verify that every checklist item marked with `[x]` or `[ ]` has corresponding code in the codebase. Check migrations, files, routes, tables, and verification items.

## Summary

All 18 phases (19-36) have been audited against the current codebase. The vast majority of functionality is implemented and present. Several minor discrepancies exist between the plan and actual implementation (table naming differences, schema variations, and a few unimplemented verification items), but no phase is entirely missing. The core architecture, routes, migrations, and domain logic for every phase are in place.

## Architecture Documentation

- **Metadata system**: Provider interface with registry pattern. Proposals stored in DB, accepted with field-lock awareness. No runtime ORM; all DB access via sqlc-generated code.
- **Magic Shelves**: Rules compiled to parameterized SQL via allowlist-based builder. Supports nested AND/OR groups up to arbitrary depth (tested 3+ levels). Count and book evaluation are separate queries.
- **OPDS**: No separate auth package; Basic Auth inlined in handler to avoid import cycles. Reuses existing `user` and `book` sqlc queries.
- **Kobo Sync**: Simplified from plan — no snapshot table; instead generates entitlement entries on-the-fly from `book` + `book_file`. KEPUB conversion cached per-file in `dataDir/kobo-cache`.
- **KOReader Sync**: Stores MD5 passwords directly (as sent by KOReader client). Links KOReader users to Lexicon users by matching username.
- **Content Restrictions**: Filter applied post-query at the service layer via `FilterBookIDs`, then used by OPDS, Kobo, notebook, and magic shelf handlers. Admin users bypass restrictions.
- **Audit Logging**: Fire-and-forget goroutine pattern so audit failures never block user operations. Async insert with `context.Background()`.
- **Recommendations**: 128-dim float32 vectors stored as 512-byte BLOB. FNV-1a hashing with fixed weights. Cosine similarity computed in Go, sorted, then capped at 3 books per primary author.

4. **Audiobook Structure Endpoint (Phase 23)**: The plan listed `GET /api/books/{id}/audiobook` for chapter/track structure. It is not present; does the frontend construct this from `book_file` records directly?
5. **i18n Completeness (Phase 35)**: Are there remaining hardcoded English strings in frontend components? A grep audit would be needed to confirm 100% coverage.
